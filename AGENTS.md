# sathian.ai Working Contract

These rules apply to the entire repository. They supplement the global Codex rules.

## Approved baseline

- The approved personal-site visual baseline is commit `1743aa2e47f669cdedc49373b35a0b3df6fd31c` on `feat/public-agent-portal`.
- The durable tag for that design is `sathian-ai-visual-baseline-2026-07-15`.
- The baseline record and golden screenshots are listed in `docs/design/SATHIAN-AI-VISUAL-BASELINE-2026-07-15.md`.
- Preserve the dark editorial system, homepage section order, large typographic hero, inline site-agent doorway, project-card composition, building-log format, and shared About/Automation shell unless Sathian explicitly asks for a redesign.
- The old priority statement in `CLAUDE.md` is historical TFN context. It does not authorize replacing the current sathian.ai personal-site direction.

## Change size

- Default to one named, local change at a time.
- Copy, article, image, project, campaign, and build-log updates should use the existing content surfaces and components.
- Do not make sitewide theme, typography, navigation, grid, animation-system, or information-architecture changes during an ordinary content request.
- Do not combine a requested content update with broad refactoring or visual cleanup.
- If a change would alter more than one major homepage section, first describe the proposed scope and obtain explicit approval.

## Visual verification

For any user-facing UI change:

1. Compare the affected page with the baseline screenshot.
2. Verify desktop and mobile layouts.
3. Run the relevant unit/type/build checks and the launch-readiness check.
4. Check keyboard use, readable contrast, overflow, and the open site-agent panel when affected.
5. Save a dated screenshot and receipt for a release candidate.

## Public and private boundary

- The public agent may answer only from published pages and approved public-memory records.
- Local second-brain files, TELOS material, family records, client material, secrets, and unreviewed notes never become public-agent context by default.
- A Toothlight must keep its three layers distinct: private memory vault, optional guardian-owned digital keepsake, and optional future fund.
- Do not claim Telegram delivery, file intake, private-memory access, autonomous recruiting, or action-taking until that exact path is deployed and proven.

## Publishing and production

- Drafting and local verification are allowed. Public posts, submissions, profile saves, and production deployment remain separate explicit approval gates.
- Never expose environment values while diagnosing or moving configuration.
- A failed release must preserve its evidence, use the documented rollback, and leave the last verified production deployment intact.
